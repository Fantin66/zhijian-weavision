# K8.5 AI Skill 专项审查

日期：2026-09-16。基线：当前 K8.5 / 0.10.5，ZhijianAI 接口 1.3。

范围：项目 skill、发行包内 skill、本机已安装 skill、设置导出的指引、编排 skill、画布 API、包数据模型。此轮只审查并生成隔离复现材料，没有修改产品、用户画布或已安装 skill。

## 结论

优先把“读素材 → 建图 → 保存 → 导出 → 读包写报告”的信息闭环做完整。当前问题涉及说明分叉、信息丢失和接口执行语义，不能只靠补写提示词解决。

## P1：优先修复

### 1. 多份指引和解析器已经分叉，升级不能自动跟进

- 项目 `.agents/skills/zhijian-ai` 的三个文件与 K8.5 发行包完全一致。
- 本机 `C:/Users/99612/.agents/skills/zhijian-ai` 的 SKILL.md、schema.md、parse-fantin.js 均与发行包不同；其解析器缺少新版 packageName 处理。
- `app.js:1865` 的 PARSE_SCRIPT 是另一份简化实现，“导出完整指引”和“复制报告指引”共用它。
- `main.js:156` 的 installFantinSkill 只检查 SKILL.md 是否存在；存在就跳过，不能判断版本或安装是否完整。
- 独立编排 skill 的 api.md 仍写接口版本 1.1；当前实际为 1.3。其 paper 风格与若干布局/字体说明也不符合当前实现。

复现：设置导出的简化解析器遇到数字类型的悬空连线端点会抛出 `.slice is not a function`，而包内解析器已有相关处理。

建议：维护一份机器可读接口定义和一份解析器；由同一来源生成界面导出、安装包 skill 和参考文档。给 skill 标明 skillVersion、apiVersion 与支持的 schemaVersion。未被用户改动的旧文件可更新；检测到用户改动时保留其版本并提供可比较的新版本，不直接覆盖。

### 2. 报告解析丢失正文与证据定位

- 权威解析器第 125 行只输出 detail 的字数，未输出正文。
- item.sourceRef、link.sourceRef 未纳入报告输出，页码、引文及定位锚点可能丢失。
- 连线批注只截取 100 字，没有另行输出全文。
- schema.md 仍以 G4 样本为主，未说明 schemaVersion:2、packageName、sourceRef 等关键字段。

复现：包含唯一标记的节点 detail 和 sourceRef 输入解析器后，两段内容均未出现在输出中。skill 却说明输出可直接理解、无需再手动解析 JSON，容易使调用者误以为已经覆盖全文。

建议：同时输出结构化 JSON 和可读报告素材；完整保留详情、批注、来源及跳转目标。长内容可分页按需读取，但必须给出读取入口和覆盖清单。附件链接使用 packageName，显示名使用 name；没有读出的内容单列，不补写成已知事实。

### 3. “AI 来源引用”被当作真实附件，保存和导出链路不完整

`aiRegisterSource` 在未提供 fileId 时，只创建元数据和 aiSource，没有 Blob。普通 saveState 与 PackageModel.encode 没有保存 aiSource。

复现：创建来源引用后，其摘要/定位没有进入包的 fileMeta；将该结构按现有包模型导入会报“附件缺失”。正常 k6Export 又要求每个非链接附件都有可读取的 Blob，因此此类条目还会阻断导出。

建议：区分真实附件、网页链接、外部来源引用。来源引用应可独立保存、重启恢复和导出，不要求虚构文件字节；支持以后补充原文件。缺原文时明确“仅有来源信息”，不能显示为已读取附件。

### 4. 成功、失败、保存与回滚的语义不完整

- 上轮已复现：异步删除项目尚未完成就返回 ok:true，备份失败也未反映在返回值中。
- 本轮复现：update_item 同时修改文字和传入非法宽度时，返回失败，但文字已改变。
- 将 saveState 的结果模拟为 false，更新命令仍返回 ok:true；aiCommit 未检查保存结果。
- 文档要求全部删除命令带 confirm:true，但 delete_item/delete_relation 的接口分支没有相应校验。测试确认缺少 confirm 仍会调用删除函数。

建议：先验证整条命令再修改；异步命令等待完成；批量执行统一提交或回滚。结果区分内存已应用与已持久化，返回错误码及受影响对象。confirm 表示调用约定，不能代替调用方实际获得的用户授权。

### 5. 有向关系可能被写成相反含义

`aiRelation` 把 A→B 和 B→A 当作同一条已有关系，但复用时没有更新端点。

复现：先创建 A supports B，再请求 B causes A，最终得到 A causes B。这会改变图中的逻辑含义。

建议：有向关系按起点、终点匹配；反向应创建新关系或明确更新端点。只有无向关系允许交换端点去重。未知关系类型应返回错误，避免静默降级为 related。

## P2：报告稳健性与说明准确性

### 6. 解析器缺少循环检测

复现两个父子循环样本：无语义连线时，节点没进入树，但输出仍提示“未发现结构异常”；连接便签后，计算 parentChain 的循环无法终止，子进程在 1.5 秒超时后被终止。

建议：建立 ID 索引、检测重复 ID 与父级循环、记录已访问节点；异常数据仍输出可读部分并给出错误清单。为文件大小、元素数和深度设限；解压使用独立目录并校验路径与体积。

### 7. 不应把旧样本结论当成格式规则

skill 和 schema 声称附件归属“只由 links 决定”、attachIds 恒为空；当前 attach 与 buildCanvas 明确使用 attachIds。

另外，普通 related 表示关联，不天然等于章节归属或证据支撑。解析器归属索引还会把节点之间的语义连线也放入列表，名称与内容不完全一致。

建议：分别保留层级、显式挂接、语义连线和来源引用。章节归属优先采用显式结构；依据内容推断的归属单独标识。parentId 用于结构组织，因果与证据关系优先用带类型的连线，避免混淆。

### 8. 文档示例应作为可执行契约测试

设置导出的 buildCanvas 示例只有 n1，却包含到 n2 的关系，原样执行会因不存在的端点失败；replace 的说明也应同时给出 confirmReplace。编排指引建议的部分样式已不支持，部分布局名会被归一到 logic。

建议：每个官方示例都在干净测试画布执行，验证结果、保存、重载和导出。用当前 capability 列表生成参数表，避免手工维护命令数量与样式清单。

## P3：值得增强的 AI 能力

1. **连接和就绪检查**：说明如何连接用户已有的页面；返回当前项目、版本、就绪状态和可用能力，防止操作了另一份浏览器数据。
2. **按需读取**：snapshot 支持指定项目/画布、分页、关系邻域与详情开关，避免每次读取全部项目。
3. **计划预检**：执行前返回新增/修改/删除数量、无效引用、重名、布局冲突及导出影响；预检本身不修改画布。
4. **证据覆盖清单**：列出每份素材已读/未读/读取失败状态，以及结论对应的文件、页码、原文位置；报告主体按用户目标组织，全量元素核对放入附录。
5. **请求去重与版本校验**：requestId 防止重试重复建图；revision 检查用户是否在计划生成后改动了画布。
6. **质量验收**：已有 skill 的重叠检查要求应配套可调用的布局检查；构建后核对孤立元素、来源缺失、无效跃迁和关系方向。

## 建议实施顺序

1. 统一 skill 分发与生成来源，修正文档和示例。
2. 修复命令事务、持久化返回值、有向关系和来源引用数据模型。
3. 修复解析器信息完整性、循环检测与报告覆盖清单。
4. 完成“真实附件/来源引用 → 建图 → 重启 → 导出 → 解析报告”端到端回归。
5. 再增加计划预检、按需读取、去重与质量检查。
